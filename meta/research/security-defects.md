# Known defects in JSON, TOML, YAML and CSV parsers — research digest

**As of 2026-10-16.** Question: What published vulnerabilities and defect classes are known in parsers of JSON, TOML, YAML and CSV (the reference implementations and the widely used parsers), and does each class have a rule in nitpick-parse that guards it?

## Answer
Eleven defect classes have published records. All but two have a guarding rule in nitpick-parse. The two without a full guard are CSV formula injection (no rule at all) and the quadratic-cost class (guarded in part; the details are in the table and in "What would change this"). Two more points are partial: a size bound the repository spells out but does not yet keep as a named constant (`NPARSE_DUP_SCAN_MAX`), and YAML alias expansion, which is guarded only by refusing aliases until a later cycle.

Two of the classes you named have thin evidence. For "invalid UTF-8, overlong forms accepted" I found no CVE for a JSON, YAML, TOML or CSV parser. The one record that fits lone surrogates is UltraJSON. For "memory exhaustion from declared sizes" none of the four formats declares sizes, so no record of that exact shape exists. The nearest records are length-limit bypasses (jackson-core) and size arithmetic in scanners (libyaml, yajl).

Evidence status: every record was read at NVD (via its API URL) or a project advisory. Only CouchDB CVE-2017-12635 has two independent primaries, NVD and the project's own advisory. All other rows have one primary per record, and each row has two records. Where a row has only one record, it says so. Statements marked "(mine)" are my inference, not a source's claim.

## What would change this
The request's trigger is "a class is one no rule here guards". Item by item:

1. **CSV formula injection (the writer emitting cells that begin `=`, `+`, `-` or `@`).** It came true: it is a published class, with CVE-2021-41270 and CVE-2023-51763 as examples, and I found no rule for it (`meta/specs/WRITER_MODEL.md:77` covers only JSON escapes). The deciding rule would be a writer rule beside W-9 and PA-061's canonical-form rule. Whether it belongs in `nparse` or with the caller is a design choice for the cycle's owner.
2. **Quadratic cost.** It came true in part. The decider is `meta/specs/VALUE_MODEL.md:155` (D-16), whose threshold `NPARSE_DUP_SCAN_MAX` is in no limits table until cycle 0.4 (PD-143's note). Two other costs have no bound at all (mine): TOML table-header and dotted-key resolution (R-11, `meta/specs/FORMATS.md:86`), and error-position counting (`meta/specs/SCAN_MODEL.md:266`, a pending measurement). The hash-flooding sub-class itself is guarded, because there is no hash container (`meta/specs/SAFETY.md:31`). Residual (mine): the opt-in index sorts on an unkeyed FNV-1a hash, so hostile equal-hash keys could degrade a lookup to a scan.
3. **YAML alias expansion.** It is guarded only by refusal (`meta/specs/FORMATS.md:114`). The budget required once full YAML ships (`meta/specs/FORMATS.md:127`) has no rule yet. If the plan wants to ship aliases before 1.0, this class has no guard.
4. **Declared or unbounded sizes.** The limits table covers one JSON string, one key, one member count and digits. It does not name a bound for a CSV field, a TOML string, a YAML scalar, or total node count and pool bytes. If the plan's PD-143 bounds are meant to cover those, `meta/specs/SAFETY.md:257` should say so.
5. **Input-size refusal.** `meta/specs/SCAN_MODEL.md:66` refuses an input over 4 GiB with `EParseState`, an error identity. `meta/specs/SAFETY.md:262` calls it a caller mistake. A service reading a hostile upload could still reach it, which sits uneasily with PA-008. This is my observation, not a source's claim.
6. **Depth, numbers, duplicate keys, UTF-8, tags, scanner arithmetic.** Each has a rule (see the table). Nothing found changes them.

## Confidence and gaps
**Medium.** Each record was read at its primary source (NVD, a project advisory or a GitHub advisory), 26 of the 30 fetches were used, and the rule citations were read in the repository. The confidence is not higher for these reasons:
- Each claim has one primary, not two. The one exception is CVE-2017-12635, which has NVD and the CouchDB advisory.
- The fetch tool paraphrased several NVD descriptions beyond a 125-character quote limit, so some quoted lines are the record's opening words. I marked those.
- Records published in 2026 (CVE-2026-18401, CVE-2026-45304, CVE-2026-49293, CVE-2026-67216) are recent. Search aggregators were my first source for their existence; each was then confirmed on NVD, GitHub advisories or the Symfony project blog.
- Unresolved: a second duplicate-key record; a second record for UTF-8 or surrogates; any CVE for a CSV parser; any record of memory exhaustion from sizes a document declares.
- `meta/roadmap/0.0/0.0.1_tools/step5.patch`, where the plan's currency table lives, was not opened. Its search for PD-140 to PD-145 found no match, so I did not check this request against that table.
- PD-143 is a planned decision. It appears in `meta/roadmap/0.0/0.0.4_tools/step1.patch` and not yet in `meta/DECISIONS.md`.
- The digest goes stale after 90 days, on 2027-01-14.
