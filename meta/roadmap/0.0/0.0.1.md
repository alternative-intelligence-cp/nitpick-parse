## 3. The steps, and what each commit carries

Each step is a worker of its own (§0's term and table). **Each commit is `git commit` of exactly what the step
staged** — `apply.py` stages its patch's files, and the worker `git add`s this file by name for the title or its
entry — never the worker skill's `git add -A` (its §6), which would take whatever else the tree holds. **The title is
committed once, at step 0**: the skill's §4 keeps it the one unstaged change until the record's commit, which a chain
of fresh workers cannot carry, since the skill's §2 reads a dirty tree as a predecessor's death; so no later commit
takes it by accident. Each commit carries the step's subject, a body saying why and the dispatch's `ATTRIBUTION`
line, with `check_refs` clean before it, its exit status read on its own line. **A worker that finds its step's input
commit is not the tree's `HEAD` stops.**

**Every step pushes, and from step 4 on its worker reads CI's run on the push**: `gh run list --repo
alternative-intelligence-cp/nitpick-parse --branch <branch> --limit 1`, then each job's log through `gh api
repos/alternative-intelligence-cp/nitpick-parse/actions/jobs/<job>/logs` (never `gh run view --log`, which can print
nothing for a log that exists — `PLAYBOOK.md` §6). Step 4's run, the first, builds the compiler (§7); wait for a run in
the background, as the worker skill's §5 says of long commands. **The run is green when** every step passes, the
emission step prints `npkc.ll == the pin's emission, 31731079 B / 1f48a31a…`, each of `llc`, `opt` and `ld.lld`
asserts 20.1.8, the harness step prints the stub's line, and the consumer exits 0. **A red run is a stop**: read the
log first; a different emission digest is a compiler defect to raise, not a pin to move.
