# 0.0.0 — the language probes — PLANNED (the execution record is appended as steps land)

> **Scope:** twelve small Nitpick programs that ask the compiler whether the
> shapes `meta/specs/` depends on are spellable, compilable and correct. No
> library code is written in this subcycle. What it produces is **a verdict per
> probe** and, where a verdict is negative, an amended specification and a
> recorded decision.
>
> **Why first.** `meta/specs/` was written against the language's
> documentation, and the compiler project's own most expensive finding is that
> *a construct that parses is not a construct that works* — most of its cycle
> 0.4 was repair, and every repair dated to the cycle that had parsed the
> construct. Several of this library's load-bearing shapes have never been
> exercised in the combination it needs.
>
> **And one probe is not like the others.** Probe 01 does not ask whether
> something compiles. It **demonstrates the central hazard**: that the naive
> decimal accumulator traps on a long number, and that the checked helper does
> not. PA-012 is the library's central correctness claim and this is where it
> stops being a claim.

---

## 1. Where you are

- Nothing is built. `src/` holds empty directories with placeholder READMEs.
- The compiler is at `../../nitpick`, cycle 1.5 (verification), self-hosting
  declared under D-202. **Do not build it from here and do not read its `build/`**: the
  artifact these probes use is the pinned toolchain the board names
  (`../BOARD.md`, W-18) — `$NPKC` and `$NPKRT`, supplied by the orchestrator or
  set by hand from `../.internal/toolchain/<commit>/`.
- There is no `nparse` harness yet. **Probes are run by hand**, one command
  each, and that is deliberate: the harness is 0.0.2 and building it against an
  unverified set of language assumptions is the mistake this subcycle exists to
  avoid.
- The probes live in `tests/probe/` and **stay in the tree permanently**. They
  are a regression suite for the language shapes this library depends on, and
  the harness picks them up at 0.0.2 as ordinary `program`-stage entries.

---

## 2. The command

For each probe, from the `nparse` tree root, with `$NPKC` and `$NPKRT` from the pinned
toolchain (the board names the commit, W-18):

```
$NPKC tests/probe/probeNN_name.npk -o /tmp/p.ll \
  && llc -O0 -filetype=obj -relocation-model=static /tmp/p.ll -o /tmp/p.o \
  && ld.lld -static /tmp/p.o $NPKRT -o /tmp/p \
  && /tmp/p ; echo "exit $?"
```

A probe that is **expected to be refused** stops at the first command, and its
verdict is the diagnostic code and span, recorded verbatim.

**Every probe exits 0 on success and a distinct positive code per assertion it
fails**, in the compiler's own house style, so a failure names itself. `exit 0`
additionally asserts, through D-151, that nothing leaked.

**Probe 01 is the exception**: half of it is *expected to trap*, and a trap
exits through `failsafe`. It is split into two programs for that reason (§4).

## 3. Decisions taken at planning

- **P-0 — a probe's filename may not begin with a digit**, so probes are named
  `probeNN_topic.npk` and the `mod:` line matches. A file's module name must
  equal its basename, and no identifier may begin with a decimal digit — D-147
  gives that opening to numeric literals alone, so `mod:01_argv;` is refused
  `NITPICK-LEX-003` with `NITPICK-RESOLVE-005` behind it. *Measured the hard
  way in `nitpick-posix`'s probe 02, 2026-09-03, after every plan in the
  ecosystem had written `01_name.npk`.*
- **P-1 — a probe is a program, never a library file.** It has its own `main`
  and `failsafe` and imports nothing from `src/`. A probe that needed library
  code would be testing the library, which is what every other cycle is for.
- **P-2 — a refused probe is a *result*, not a failure of the subcycle.** Probe
  05 is expected to be refused and probe 01a is expected to trap; their value is
  the exact diagnostic and the exact trap code. The subcycle fails only if a
  verdict is *undecided* — a compiler crash, a hang, or output nobody can read.
- **P-3 — the verdict is recorded before the next probe is written.** A batch
  of twelve written and then run together is a batch where the fourth one's
  answer would have changed the fifth one's design.
- **P-4 — a negative verdict amends `meta/specs/` in the same commit.** Not a
  note to self, not a TODO. The specification is the authority (PA-002) and an
  authority known to be wrong and not corrected is worse than none.
- **P-5 — the probe programs stay.** They become `tests/probe/`'s permanent
  suite, so a compiler change that breaks one of these shapes is caught by
  `nparse`'s own harness rather than by a format failing mysteriously in 0.8.

## 4. The probes

Each entry: **what it asks**, **the shape**, **why it matters**, and **what a
negative verdict costs**.

### 01 — the no-trap accumulate — **the flagship**

Two programs, because one of them is expected to trap.

**01a — `probe/probe01a_naive_accumulate.npk`, EXPECTED TO TRAP.**

```nitpick
// Feed the digits of "99999999999999999999999" — 23 of them — to the accumulator
// every parser in every other language writes.
int64:acc = 0i64;
for (int64:i in 0i64...23i64) {
    acc = acc * 10i64 + 9i64;     // D-210: this traps
}
exit 0i32;                        // NOT REACHED
```

with a `failsafe` that reports `IntOverflow` by exiting a distinct code.

**Asks:** does D-210 actually trap here, and with which code?

**01b — `probe/probe01b_checked_accumulate.npk`, EXPECTED TO EXIT 0.**

```nitpick
func:mul_add = uint64?(uint64:acc, uint64:base, uint64:digit, uint64:bound)
        never fails {
    if (base == 0u64)   { pass NIL; }
    if (digit > bound)  { pass NIL; }
    uint64:room = (bound - digit) / base;
    if (acc > room)     { pass NIL; }
    pass (acc * base + digit);
};
```

driven with the same 23 digits, plus 5000 digits, plus `bound` at
`UINT64_MAX`, `INT64_MAX` and `0`, and `base` at 2, 8, 10 and 16 — asserting
`NIL` where it must overflow and the right value where it must not.

**Matters because** this is `SCAN_MODEL.md` §5 and PA-012, the library's central
correctness claim. It is also the single most likely place in the whole plan to
write a remote denial of service, and the two programs side by side are the
evidence that the rule is real rather than defensive.

**A negative verdict on 01a** — if the naive form does *not* trap — would mean
D-210 does not apply as read, which changes `SAFETY.md` §4's whole framing and
is a finding worth the whole subcycle on its own.

**A negative verdict on 01b** — if the checked form traps anywhere — means the
guard order is wrong, and the fix is found here rather than in cycle 0.1 with
five formats built on it.

### 02 — a 24-byte POD in a `Vec`

```nitpick
struct:Ev = { uint8:kind; uint8:scalar; uint8:flags; uint8:pad;
              uint8:tsrc; uint8[3]:tpad; uint32:tlo; uint32:thi;
              uint32:slo; uint32:shi; };
```

**Asks:** `#size_of<Ev>()` — **assert it is 24** — and a `Vec<Ev>` of 100 000:
fill, read back, copy the whole vector, compare, clear, free, exit 0.

**Matters because** `Event` is exactly this (PA-021) and the event ring is
exactly this array. A padding surprise changes the specification's number, and
finding that out from a benchmark rather than a test is the wrong order.

**A negative verdict costs** the `Event` layout, and `EVENT_MODEL.md` §2's
table is re-derived from what the compiler actually lays out.

### 03 — a tagged enum with a struct payload

```nitpick
struct:Fault = { uint16:code; uint16:flags; uint32:lo; uint32:hi;
                 uint32:expected; uint32:found; uint32:depth; };
enum:Step = { Ev(Ev); Fault(Fault); Done; };
```

**Asks:** destructuring both payload arms in a `pick`, storing `Step` in a
`Vec`, `#[derive(Eq, Debug)]`, and `#size_of<Step>()` recorded.

**Matters because** `Step` is the library's whole interface (PA-023) and the
argument for it — that `pick` exhaustiveness forces the caller to handle a
fault — depends on the shape existing.

**A negative verdict costs** the interface: the fallback is a `Step` struct with
a kind tag and both payloads inline, which is bigger and loses the
exhaustiveness argument that is the entire reason for the design.

### 04 — an arena of POD nodes, and the copying `get`

```nitpick
struct:Node = { uint8:kind; uint8:flags; uint16:pad; uint32:len;
                uint64:a; Handle<Node>:first; Handle<Node>:next;
                uint32:slo; uint32:shi; };
arena<Node>:ar = arena_make(4096i64);
```

**Asks:** `alloc`, `put`, `get` (**and that it returns a copy**), `free`, a
handle used after `free` answering `StaleHandle` (−4106) rather than trapping,
`reset`, and `destroy` consuming the arena. Also `#size_of<Node>()`.

**Matters because** `Document` is exactly this (PA-030), and the
generation-checked stale handle is the use-after-free guarantee the value model
rests on.

### 05 — an arena whose element owns a string — **EXPECTED REFUSED**

```nitpick
struct:Owning = { string:text; uint32:n; };
arena<Owning>:ar = arena_make(16i64);
Owning:back = ar.get(h) ? Owning{ text: "", n: 0u32 };   // expected: refused
```

**Asks:** does the copy that `arena.get` performs collide with TYPE-046's
refusal of a copy of an owning value?

**Matters because** it is **the forcing rule behind the entire value model**.
`VALUE_MODEL.md` D-1 asserts that a node holding a `string` "would not compile",
and this is where that stops being an assertion. If it is *accepted*, the node
layout could hold text directly and the pool becomes an optimisation rather than
a necessity — a materially simpler library.

**Record the diagnostic code and span verbatim either way.** This is also the
probe whose result becomes O-N4's evidence.

### 06 — a trait with a `Self->` receiver through a generic bound

```nitpick
trait:Src = { func:step = Step(Self->:self); };
func:drive<F: Src> = int32(F->:f) { … };
```

**Asks:** two impls, dispatched statically through the bound.

**Matters because** this is the `Format` trait exactly
(`PLUGIN_MODEL.md` §2), and static dispatch through a bound is the intended
path for every consumer.

### 07 — the same trait through `dyn`

**Asks:** `dyn Src` constructed from both impls, `step` called through it.

**Matters because** PA-071 claims `Format` is object-safe and that `dyn Format`
is the runtime-format-choice path. The object-safety rules (`TRAITS_REFERENCE.md`
§4.2) say it should be — a `Self->` receiver is admitted, there is no `Self` in
the return, no associated type, no generic method — but "should be" is what this
probe converts into "is".

**A negative verdict costs** the runtime-choice path only: `builtin_open` would
return a concrete enum the caller `pick`s over, and `PLUGIN_MODEL.md` §2's `dyn`
paragraph comes out. Static dispatch is unaffected, so this is the cheapest
negative in the set.

### 08 — a `uint8[]` borrow at the four escape-analysis edges

**Asks**, as four separate compilations:

| Edge | Expected |
|---|---|
| passed down two call levels | accepted |
| returned from a function | refused |
| stored in a struct that outlives the call | refused |
| a `Cursor` struct holding one, built by literal and passed down | accepted |

**Matters because** the whole library reads through a `uint8[]` view of the
caller's input (PA-010) and `Cursor` holds one (`SCAN_MODEL.md` C-2). The fourth
edge is the one the design actually depends on and the one most likely to
surprise.

**A negative verdict on the fourth** costs the `Cursor` type: every scanning
function takes `(src, pos)` as two parameters and returns the new position,
which is workable, uglier, and much better known now.

### 09 — `move T:v` into a generic container

**Asks:** `vec_push<T>(v, move T:x)` for `T = int32` and for `T` an owning
struct holding a `string`, including the container's drop and `exit 0`.

**Matters because** `Vec<T>` (PA-004) must hold both: the parser's frames are
POD and a `Document`'s pool-free path holds owning values.

### 10 — a 50 000-deep structure with an explicit stack

**Asks:** build a 50 000-level nested structure using a `Vec<Frame>` rather than
recursion, walk it, free it, exit 0. **And, as a second program**, the recursive
version — with its result recorded.

**Matters because** PA-022 forbids native recursion on an input-controlled path
and `SAFETY.md` §5 justifies it by the *absence* of a stack-depth guard (O-N2).
This is where that absence is demonstrated rather than cited.

**Needs care:** the recursive version may take the process down in a way that is
not a clean `failsafe` exit. Run it last, expect a raw fault, and record what
the shell reports.

### 11 — `Bytes` growth

**Asks:** a million single-byte appends into a doubling `buffer`-backed sink,
with the **reallocation count** counted and asserted below `log2(1e6) + 2`.

**Matters because** the compiler measured exactly this shape as quadratic in
`npkg`'s first full run — seventeen minutes of fifty-six spent in the kernel —
and every writer and every escaped scalar in this library goes through it.

### 12 — module-level state

**Asks:** a `fixed` module-level table (the 256-byte class table's shape) read
from ordinary code; **and** a plain reassignable module binding, expected
refused with D-211's code.

**Matters because** `SCAN_MODEL.md` C-8 needs the first, and the second is what
makes the prototype's five format parsers unbuildable as written — a fact this
library's README states and should therefore have verified.

## 5. The steps

Each step is one commit.

**Step 1 — the flagship, first: 01a and 01b.** The library's central claim, and
a negative verdict on either re-frames `SAFETY.md` §4 before anything else is
written. Record both verdicts, then continue.

**Step 2 — the value-model probes: 04, 05, 02, 03.** In that order, because 05's
verdict decides whether the pool is a necessity or an optimisation, and that
changes what 02 and 03 need to be.

**Step 3 — the dispatch probes: 06, 07.**

**Step 4 — the remainder: 08, 09, 10, 11, 12.**

**Step 5 — the record and the amendments.** Every verdict written into §7 below;
every consequence written into `meta/specs/` and `meta/DECISIONS.md`;
`tests/probe/README.md` written, saying what the directory is for and that a
probe is never deleted.

## 6. What the executor should know

- **The reserved words will bite immediately.** `end`, `in`, `limit`, `any`,
  `buffer`, `raw`, `move`, `error`, `on` — `specs/BUILD.md` §7 is the list. A
  probe about spans wants a local called `end` and a probe about input wants one
  called `in`; neither is available. Use `hi` and `src`.
- **`discard(x);` takes parentheses. `defer { … }` takes no trailing
  semicolon.** Declarations end `};`; control-flow blocks do not.
- **Adjacent string literals do not concatenate.**
- **A file's `mod:` name must equal its basename**, or the loader reports
  `NITPICK-RESOLVE-005` at line 1 and says nothing about the name.
- **Strings are move-only** (TYPE-046). Build a name per use rather than holding
  one binding across lines.
- **A `failsafe` must name every reachable error** (REACH-002), including the
  system ones the program's own machinery can raise — and probe 01a's `failsafe`
  must name `IntOverflow` specifically, which is the point of it. Copy the arm
  set from `../../nitpick/tests/backend/programs/proc_tool.npk` and prune.
- **Exit 0 means "and nothing leaked"** (D-151). Every probe except 01a exits 0
  on success on purpose.
- **`llc` and `ld.lld` must be the pinned 20.1.2.** `llvm-config --version`.
